# Run attachments

Users can attach local images and documents to an Agent Run (trial consoles and
Hosted service order forms). Core stores them only in a dedicated local
directory and puts a short-lived capability link into the Run input; the Agent
(for example Agent Node) downloads the link. Core never opens, converts or
executes attachment contents.

## Enabling

| Variable | Default | Meaning |
|---|---|---|
| `OPENLINKER_ATTACHMENTS_DIR` | unset (disabled) | Absolute path of a dedicated directory. Created `0700` if missing. Refused if it is a symlink, not owned by the Core process user, grants group/other permissions, is the filesystem root, or lies inside a system temporary directory. |
| `OPENLINKER_ATTACHMENTS_PUBLIC_ORIGIN` | `API_URL` | Origin used in capability links. Use the main https site so trial-console previews pass the page CSP. |
| `OPENLINKER_ATTACHMENTS_SHARED` | `false` | Must be `true` (with one shared volume mounted by every replica) when `RUNTIME_HA_MODE=true`; otherwise attachments stay disabled. |
| `OPENLINKER_ATTACHMENTS_OWNER_MAX_COUNT` / `_OWNER_MAX_BYTES` | `40` / `1000000000` | Live (unreleased) attachments per account. |
| `OPENLINKER_ATTACHMENTS_INSTANCE_MAX_BYTES` | `10000000000` | Total stored bytes. |
| `OPENLINKER_ATTACHMENTS_UNBOUND_TTL_SECONDS` | `86400` | Lifetime of an upload no Run has used. |

Uploads are also refused while the directory's filesystem has less than 2 GB or
10% free (whichever is larger). Misconfiguration disables the feature with a
log line; Core keeps starting.

## API

- `POST /api/v1/attachments?filename=<display name>`: raw file bytes as the body,
  JWT or User Token with `agents:run`. Any file type, at most 30 MB. Returns
  `{url, kind, media_type, filename, size, sha256, expires_at}`; `kind` is
  `image` for JPEG/PNG/WebP/GIF by signature, otherwise `file`. Errors: 413, 422
  (empty), 429 (account quota), 503 (storage full or unavailable). The global
  8 MB body limit does not apply to this route only.
- `GET /api/v1/attachments/:token`: no login; the link is the capability.
  Images are served inline with their type; everything else as
  `application/octet-stream` with `Content-Disposition: attachment`. Always
  `nosniff`, `no-store` and `Content-Security-Policy: default-src 'none'; sandbox`.

## Runs

Top-level input fields named `image_url`, `image_urls`, `file_url`,
`file_urls` or ending in `_image_url`, `_image_urls`, `_file_url`,
`_file_urls` (string or array of strings) carry attachments; at most 20 links
per Run. When a Run is created, each link issued by this Core must belong to the
caller, be live and unused, otherwise creation fails with 422
`ATTACHMENT_NOT_OWNED`, `ATTACHMENT_EXPIRED`, `ATTACHMENT_LIMIT` or
`ATTACHMENT_INVALID` (details carry the field). Links to other sites pass
through unchanged. Valid attachments are bound to the Run (single use) and kept
until it is terminal.

## Storage and cleanup

Layout under the directory (all directories `0700`, files `0600`, all paths
generated by Core and accessed through `os.Root`): `blobs/` contents with
random names unrelated to the token, `meta/` JSON metadata (the token only as
SHA-256), `tokens/`, `owners/` and `runs/` indexes, `tmp/` in-progress writes.
Uploads stream into `tmp/`, are bounded and hashed while reading, synced and
renamed into place before metadata appears.

A sweeper runs at start and every 5 minutes: it releases attachments of Runs
that are terminal or no longer exist, deletes expired uploads (bound ones after
at most 7 days), and removes orphaned contents and temporary files older than an
hour. Contents never enter PostgreSQL, Redis, Run events or conversation history.
Back up nothing here: losing the directory only affects Runs still in progress.
